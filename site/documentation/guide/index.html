User guide

User guide#

Learn how to install Handshake, run your first workflow, and work with coding agents in your folders.

Install#

Handshake requires macOS 26+ on Apple Silicon.

Install it with Homebrew:

brew install --cask standing-desks/tap/handshake

Then open Handshake from Applications.

To install manually instead, download the .dmg from the latest release, open it, and drag Handshake onto the Applications folder in the disk image. Wait for the copy to finish, eject the Handshake disk image in Finder, and open Handshake from Applications.

Releases are Developer ID signed and notarized. The license is included inside the installed app bundle.

To update a Homebrew install, quit Handshake and run brew update && brew upgrade --cask standing-desks/tap/handshake. To update a manual install, quit Handshake, open the new DMG, and drag Handshake into Applications, choosing Replace when Finder asks. Your saved work and settings are retained.

Upgrade from Twine

Quit both apps before upgrading. New installs use brew install --cask standing-desks/tap/handshake. Existing twineproject/tap users can stay on that tap. After the tap rename migration is available, run:

brew trust --cask standing-desks/tap/handshake
brew update
brew upgrade --cask standing-desks/tap/handshake

Homebrew 6 and newer require explicit trust for the renamed cask; trust in the old name does not follow the rename. Omit the trust command on older Homebrew versions that do not provide it. See Homebrew's tap trust guidance. For the compatibility tap, use twineproject/tap/handshake in both the trust and upgrade commands. The historical twine-app and twine-ade casks map to handshake.

For manual replacement, copy Handshake.app from the DMG into Applications, replace an existing Handshake copy, and move the old Twine.app to Trash. Normal app removal or brew uninstall --cask handshake preserves saved data; avoid --zap when keeping it.

The first production launch adopts ~/Library/Application Support/Twine/ into ~/Library/Application Support/Handshake/, including sessions, transcripts, trace details, attachments, and workflow layouts. It adopts $XDG_CONFIG_HOME/twine/ into the sibling handshake/ config root (default ~/.config/), with imports, workflows, and themes. An existing Handshake root wins without being overwritten. Existing preference domains preserve launch choices, models, and zoom. Debug, preview, and test data stay isolated.

The legacy roots remain available for recovery. Quit both apps, move the new Handshake root aside, and either use the old app with its retained Twine data or relaunch Handshake to retry migration. Changes in copied roots are not mirrored back to the legacy root. Symlink-managed config roots and linked files keep sharing their original targets, so edits are visible through both names. Keep a separate backup of those targets to roll back their contents. Quit the old app if migration reports that its data is in use.

HANDSHAKE_DATA_DIRECTORY, HANDSHAKE_CONFIG_PATH, HANDSHAKE_PREFERENCES_SUITE, and HANDSHAKE_HARNESS_PATH take precedence over their corresponding TWINE_* inputs. Explicit data/config overrides skip default-root migration. Config paths must be absolute; an invalid present new value does not use the legacy fallback. Old twine_light/twine_dark selections, imports, and customized theme files still resolve, with the existing Silica compatibility behavior preserved.

Run your first workflow#

  1. Open Handshake and choose Open Folder… (⌘O) to select the folder you want to work in.
  2. Create a session to keep the workflows for your task together.
  3. Add a workflow in a new tab (⌘T). Choose Terminal for a shell, or Single agent to work with a coding agent. For an agent workflow, install and authenticate its harness separately, then select it in Handshake's launch form.
  4. Start the workflow and enter your command or task in its terminal.

You can return to the session later to review its output or continue working. The sections below explain how to use more workflows and organize your work.

Folder windows#

Open Folder… (⌘O) reuses an empty window or opens another window when a folder is already open. New Window (⌘N) opens a start page. Opening a folder that is already open focuses its existing window, including when opened through a symlink.

Each window has independent sessions, terminals, file tabs, and navigation. Menu commands act on the focused window. Settings, recent folders, and custom workflow types are shared. Closing a window stops only its folder's processes; Close Folder returns that window to the start page. Quitting stops every window's processes and restores all open folders on the next launch. Unavailable folders show an explanation and can be closed without reopening them next time.

Use View → Zoom In (⌘+), Zoom Out (⌘−), and Actual Size (⌘0) to scale the interface from 50% to 200%. Zoom applies to every window, including terminals, editors, previews, and dialogs, and is remembered between launches.

Files#

The sidebar starts open. Toggle it with the toolbar button or ⌃⌘S to browse the folder or make more room for terminals. Expanding a directory loads only its children; empty directories remain visible. Handshake refreshes expanded directories and the selected file when they change, including changes made by shells and agents.

Files also shows Git status for each repository’s primary checkout, including repositories inside a non-Git folder. Repository roots use the same folder icon and change dot as other directories. Badges mark modified (M), added (A), deleted (D), renamed (R), copied (C), type-changed (T), untracked (?), and conflicted (!) paths. Filled badges indicate staged changes; a file can have both staged and unstaged badges. Click a badge for details. Deleted tracked paths remain visible with a strikethrough; folders with changed descendants have a dot.

Git status refreshes automatically and is read-only. A clean checkout can still have commits ahead of its upstream. Additional linked worktrees are not included yet. Discovery skips Git internals and common dependency/build directories; if discovery reaches a limit, open a smaller folder to inspect the remaining repositories.

Select a file to make small edits to UTF-8 text up to 2 MiB. Use ⌘Z to undo, ⇧⌘Z to redo, and ⌘L to go to a line. Edits save automatically after a short typing pause, including in background tabs. You can keep typing during saves or press ⌘S to save immediately, even with autosave disabled or a longer delay. Configure autosave in Settings. Unsaved changes show “Edited” in the header. Settings still require an explicit Save. Before saving, Handshake checks whether the file on disk has changed. If it has, choose Reload to discard your edits or Overwrite to save them; Cancel keeps the edits without changing the file. Autosave pauses after a conflict or save failure. Use File → Save or ⌘S to retry; successful saving or reloading resumes autosave. Disk updates refresh clean files and never replace unsaved edits. ⌘W closes the file and returns to the workflow. Binary files, larger files, deleted paths, symbolic links, and special files show an explanatory state. Up to 256 directories can be expanded at once.

The native editor automatically highlights HTML, CSS, Swift, Rust, Python, C, C++, C#, Go, Java, Ruby, JSON, JavaScript/JSX, TypeScript/TSX, TOML, YAML, and shell files. HTML and Markdown files open in Preview; switch to Source to edit with highlighting. Markdown previews follow local links. It detects languages from filenames and script shebangs. Use the language menu in the file header to choose a language, restore Automatic detection, or select Plain Text. The choice stays with that open file tab and never changes the saved text. Colors update as you type and follow the system appearance. Unknown languages and files that exceed the highlighting work budget remain editable as plain text. Shell highlighting uses the Bash grammar; embedded languages in HTML <script>/<style> blocks, strings, or Markdown code fences are not highlighted separately.

Memories#

Choose Memories at the bottom of the sidebar to inspect local Codex and Claude Code memory. It expands below compact Files and Sessions headers; clicking Memories again collapses its navigation while leaving the reader open. Click Files or Sessions to restore the normal sidebar lists.

Switch between This workspace, Global, and Other workspaces. Each location remembers its selected source, search, harness and kind filters, and source-list position, including after relaunch. Other workspaces has a store picker for memories from other checkouts or stores that cannot be associated with the open folder. Rows identify their harness and, for other workspaces, their store. Search filenames and paths, filter by harness or kind, and use the refresh arrow to rescan disk. The reader's info button shows the full path, provenance, type, and modification date.

Markdown opens rendered, with headings, lists, tables, and links. Switch to Markdown to inspect the original text, including any frontmatter. Choose Edit to open a local Markdown file in Handshake's editor. Memory edits follow the same autosave setting and delay as other file edits. Use File → Save or ⌘S to save immediately, or to save manually when autosave is disabled. If the harness changes the file, Handshake offers Reload or Overwrite before replacing it. Unsaved edits remain in their file tab when you return to Memories.

SQLite records, settings summaries, and other non-Markdown sources remain read-only. The viewer includes generated memory, instructions, rules, agent memory, skills, and extension resources. A file existing on disk does not prove that a running harness has loaded it. Folder-associated files can live outside the opened folder. Rendered memories do not load remote images or scripts; clicking an external link opens your browser.

Memory viewing uses local files without starting a harness or requesting cloud memory. Known synchronized Claude mirrors are excluded. Missing, unreadable, binary, or oversized sources show an explanation. Text reads are limited to 2 MiB; discovery is bounded to 1,024 sources and directory entries, 32 databases, and 256 recent extraction records per database. Memory trees are scanned eight levels deep and folder instructions six levels deep. The checked-locations menu shows discovery diagnostics. Return to workflows by clicking the Sessions header.

Sharing memories between agents#

Handshake can automatically share project memories between Codex and Claude Code as an opt-in beta. To enable sharing:

  1. Open Settings → Experimental and enable Cross-agent memory consolidation, labeled Beta. The feature defaults to off, saves immediately, and applies to every open folder.
  2. Open your project folder and turn on the Share switch beside Memories. This switch controls sharing for that project and remains available when Memories is collapsed.
  3. Start a fresh Codex or Claude Code conversation through Handshake to use newly available memories.

The gear beside Share opens Memory settings, with sharing status, project-memory previews, and storage details. Sharing runs automatically; Check now requests an immediate check. Refresh sources rescans the ordinary memory browser.

Turn off Share to pause sharing for the project while retaining its saved memories. Turning off the app-wide experimental feature stops new capture and delivery for all folders and hides the sharing controls. Ordinary memory browsing remains available.

The app-wide setting is stored in the main configuration file:

[experimental]
cross_agent_memory_consolidation = true

Handshake automatically renames older [feature_flags] sections to [experimental] before loading settings, including sections in imported configuration files. Saved choices and import precedence are preserved. If both sections exist in the same file, explicit [experimental] entries take precedence. Files already using the new name are left unchanged. An interrupted migration resumes on the next attempt. If a file cannot be safely migrated or written, Handshake reports its path and retains the source for repair or a manual section rename before retrying.

Agents load native memories on their own schedule. An active destination session can delay delivery, and Codex's native memory generation can wait for its quota guard. Existing conversations can retain older context; a delivered file does not guarantee immediate recall. In Memory settings, right-click a project memory and choose Correct memory… to save a brief replacement and archive the old claim and summaries linked to it. Adding a separate note does not replace an earlier memory. Prompt refresh selects relevant memories within a bounded payload and identifies omitted content for retrieval. Handshake's local consolidation makes no model calls.

Agent workflows#

Choose Adversarial, Coordinator, or a saved workflow from a new tab. Pick a harness for each agent, and optionally its model and effort level, then start it. Supported harnesses are Codex, Claude Code, pi, Antigravity (agy), OMP (omp), OpenCode (opencode), and Kiro CLI (kiro-cli), installed on your shell's PATH. Choose a model and effort level from the options shown in the launch form. Claude Code also accepts a model name you type yourself. Where available, YOLO lets the harness run without asking for permission before each action. Pi does not ask for permission, so it has no YOLO option. Built-in workflows wait for a task in the first agent's terminal. Instructions use the harness instruction channel. Setup does not start agent work. Work moves through the graph's links. Harnesses run directly in the open folder. Kiro uses its V3 engine and native login (kiro-cli login). Handshake supplies a temporary named profile for its hooks and role instructions. Kiro may ask you to trust a newly opened folder before continuing.

Each agent has a terminal subtab. Review rounds reuse the agent's live harness conversation when it remains available. After an agent completes its work, its terminal stays interactive. After a workflow completes or reaches its review limit, give a start agent another task to start a new cycle with the same conversations and trace history. Older stage workflows also have Individual mode for separate follow-up conversations. Restored workflows resume recorded harness conversations when all unfinished active agents have compatible session handles.

Click the + button to open a new tab. The workflow chooser has two grids: Built-in and Your workflows. Choose Create your own to open the native graph editor in that tab. Add agents and enter their instructions. Drag agents to move them. Drag between an output circle and an input circle to connect agents. You can start at either end. Ports of the same type cannot connect. You can also click the circles. Click an agent or link to change its settings. The editor has compact cards on a dotted canvas. Use Fit to see the full graph. The name and description fields are above the canvas. A valid receiving card lights up as you drag a connection. You can also use Connect to… under Actions in agent settings or in a card's context menu. Settings keep your draft edits when you click outside them. The Agent view contains the name, color, and instructions. Choose a color to tint the card and its outgoing links. Incoming work settings appear when an agent has multiple input links. Use When work ends to send a result or make a review decision. Right-click an agent and choose Duplicate agent to add another agent with the same settings. Switch to Launch defaults to set optional harness, model, effort, and permission choices. These choices fill the launch form. You can change them before starting. Right-click empty canvas space for workflow settings and the activation limit under Advanced. Double-click empty canvas space to add an agent at that point.

Each graph node is an agent. Agents with no forward input links start the workflow. If there are multiple start agents, they receive the same task and can work at the same time. A Work complete link sends a complete result. An Item ready link sends one piece while the source keeps working. A busy receiver queues new pieces. Use Start as work arrives to process items one at a time, or Wait for every incoming link to wait for one result from each input. Use Approved and Changes requested links for review. Add another event in a link's popover to send both pieces and a final result between the same agents.

Agents with no forward output links return the final results. Feedback links do not change which agents start or return results. Workflow settings offer Wait for all results, Choose a result, and Compare times. Each option waits for active work to stop. Choose keeps all outputs and lets you select one. Compare times shows the time from task delivery to explicit completion for each final agent. A bounded activation limit stops repeated feedback loops. A graph can use up to five interactive agents, 32 total nodes including decisions, and 64 links.

Enter a name and use Save or ⌘S. Use ⌘Z to undo edits. The editor enables Save when the current graph is valid. From a launch form, Edit Workflow opens the editor in the same tab. Changes to a built-in save as a user workflow.

Adversarial and Coordinator ship as TOML files and use the same agent graph format as user workflows. Adversarial connects an Implementer to a Reviewer. The Reviewer can approve the result or send feedback. Coordinator connects a Planner to Worker 1 and Worker 2. Both workers receive the plan and work on their named parts. Their results go to a Coordinator, which waits for both and checks the combined work. The default files are included in Handshake.app/Contents/Resources/workflows.

Decision nodes

Double-click the workflow canvas to create an agent, then switch Node type from Agent to Decision in its configuration popup. The node becomes a diamond. Its left connector accepts incoming work; drag repeatedly from its right connector to connect receiving agents or other decisions.

With one outgoing connection, the node is a Passthrough: it forwards incoming work directly, makes no decision, and does not require Nouli. With two or more connections, Nouli chooses one route. Install the nouli executable on your PATH and configure its provider before running a workflow that needs a model decision.

Enter routing instructions and fill in one criterion for each connected destination in Routes. Adding a wire adds a route; deleting it removes that route. Four connections require four configured options. Missing criteria and incomplete or duplicate mappings prevent saving or starting the workflow. An unconnected decision needs an output. Click a connection’s label to edit its criterion directly.

Enter a task in the launch form, or in a starting decision’s input surface. Each model decision captures its incoming evidence and can include the original task. Only the selected route activates work. Unselected terminal roles do not need to produce results. Conditional branches must use Start as work arrives when waiting for alternative branches would block a join. Small decision graphs fit at up to 80% scale; the existing zoom controls adjust the view.

Launch defaults offers optional Nouli provider-profile and model overrides. Empty fields use Nouli’s configured defaults. Inspect captured inputs and typed outcomes in a decision’s subtab and Traces. Refusal or provider failure pauses without choosing a route. Retry captured decision retries frozen inputs using the configured provider settings. Calls use --no-session; Handshake retains the workflow evidence and trace history. A chained example is in examples/workflows/decision-triage.toml.

Start a graph, then enter the task in the first agent's terminal. Use Results to read all final outputs, select a result, or compare times.

Handshake saves user types as versioned TOML files in $XDG_CONFIG_HOME/handshake/workflows. The default path is ~/.config/handshake/workflows. Copy a .toml file to this directory to share or import a type. You can rename the file and keep it in version control. Keep its id when you move or share it. Use Create your own or edit a built-in to create a separate identity. The chooser refreshes after file changes. Invalid files are skipped. A save conflict preserves external edits. Reopen the type to load those edits before you save again.

New graph files contain schema_version = 2, an id, a version, and a definition. The definition has roles and a graph. Each graph edge has a stable id, from, to, and event. Events are done, piece_ready, feedback, and approved. Endpoints use role IDs. Version 1 files with task and finish endpoints remain readable. Receive rules are any or all; Finish is all, choose, or timed. Saved versions stay in .history. Existing SQLite types export once; a deleted exported file stays deleted. Started workflows keep their complete original definition. Older ordered stage definitions remain readable. The editor converts them to graphs before saving. New saves must use graphs.

Agents send work through their links when they explicitly report completion. Terminal text and process exits do not advance a workflow.

Mark done… is always available for an unfinished active role, including after its process exits. Its form also supports review decisions and worker assignments. Review loops stop at the type's limit; Cancel workflow stops all its agents. Runs restored after quitting or a crash resume their unfinished active agents when every one has a recorded harness session. Otherwise they remain interrupted with their saved output. The Traces panel shows each role's stage invocations on compact agent tracks in shared start order, with equal spacing regardless of pauses. Select a step to focus a seven-step window and inspect its stage changes, completions, and handoffs; this history survives reopening the app.

Traces opens in Overview, with steps in start order. Switch to In Depth to inspect the selected step on a timeline of elapsed time: tool calls, parallel subagents, and previews of their inputs and outputs. Search the activity, show only failures, and jump from an activity to its recorded output.

Claude Code, Codex, pi, OMP, and Kiro can show prompts, tool calls, and responses in Traces. Select a step to jump to its recorded terminal output. Antigravity and OpenCode show workflow activity but do not record individual prompts or tool calls, so In Depth has no detailed activity for them. If detailed tracing is unavailable, you can still use the agent's terminal and review its saved output. Handshake leaves your harness configuration files unchanged.

Configuration#

Handshake reads $XDG_CONFIG_HOME/handshake/config.toml at startup, falling back to ~/.config/handshake/config.toml when XDG_CONFIG_HOME is unset, empty, or relative. It creates a small starter config and themes/handshake_dark.toml and themes/handshake_light.toml beside it on first launch. Existing files are never overwritten. When upgrading from Silica, customized default palettes are copied into the new default files once; untouched palettes adopt the Handshake colors. Silica remains available through themes/silica_dark.toml and themes/silica_light.toml imports.

Choose Handshake → Settings… or press ⌘, to edit the config file in a popup attached to the current window. Save with ⌘S or File → Save. Valid settings apply immediately to every open folder; invalid settings keep the previous file and active settings. Unsaved edits are protected when closing the window or quitting, and external file changes prompt you to reload or overwrite.

[appearance]
color_scheme = "system" # "system", "light", or "dark"

[terminal]
font_family = ""
font_size = 13.0

[editor]
autosave = true
autosave_delay_ms = 500

File edits autosave by default after a 500 millisecond typing pause. Set editor.autosave = false to save manually, or change editor.autosave_delay_ms to a positive whole number of milliseconds (for example, 2000 for two seconds). Saving Settings applies these changes immediately to every open file tab. ⌘S always saves immediately, including when autosave is disabled. Settings, workflow designs, and session forms use explicit saving through File → Save or ⌘S; session names also accept Return.

Terminal settings apply to live shell and agent terminals, including Bento panes, and terminal history. When font_family is omitted or empty, Handshake uses its private bundled Hack Nerd Font at 13 points by default, including bold and italic faces. The bundled font is available only inside Handshake; it is not installed into Font Book or exposed as a selectable family. To choose a custom font, install it in macOS and set its family name (for example, font_family = "JetBrains Mono"). Custom names resolve only to installed fonts, including a separately installed copy of Hack Nerd Font. Handshake checks that i and w have equal character widths, allowing Nerd Fonts whose icons are wider. An unavailable font or one that fails this check falls back to system monospace with a warning. font_size defaults to 13 points and accepts sizes from 6 through 72, including fractional sizes such as 13.5. appearance.color_scheme selects system, light, or dark appearance for all app windows.

Select a different palette for each appearance with an optional [theme] table:

[theme]
light = "handshake_light"
dark = "handshake_dark"

Names omit the .toml extension and resolve to themes/<name>.toml beside the main config file. Either key can be omitted to keep its default. Spaces in filenames are supported; use a filename basename rather than a path. For example, choose light = "catppuccin_latte" and dark = "catppuccin_mocha", or select silica_light and silica_dark to restore Silica.

Selected theme files supply terminal colors for that appearance only; other settings in those files apply only when loaded through a global import. A theme can import another color file. Missing or invalid selected files produce configuration diagnostics and use the complete defaults. Unselected theme files are left alone. The starter config includes only appearance, font, and theme choices; use this guide for additional options.

A top-level import loads one or more complete TOML configuration files. Put it before any table headers in config.toml:

import = ["themes/handshake_dark.toml", "fonts.toml"]

[terminal]
font_size = 14.0

[terminal.colors]
# Settings here override the imported files.
background = "#101820"
foreground = "#e5e1cf"
cursor = "#8fbe5c"
selection = "#34495e"

A single file can also use import = "themes/handshake_dark.toml". Files merge in the order listed: later imports override earlier imports, then the importing file overrides them all. Tables merge recursively, so overriding terminal.font_size preserves an imported terminal.font_family. Individual terminal colors merge by name. Global imported colors override the selected palettes in both appearances, and inline [terminal.colors] values override those imports. Defaults fill omitted settings after merging. Imported files can contain any supported settings, including appearance and terminal fonts.

Imports accept absolute paths, ~/ paths, and paths relative to the file containing the import. Imported files can have their own top-level imports. Cycles are rejected, including cycles through symlinks; each import tree is limited to 64 levels and 256 documents. Invalid imported settings cause the complete config to fall back to defaults even if a later file overrides that setting. Diagnostics identify the original file, line, and key. Missing imported files are reported and never created.

Terminal colors normally come from themes/handshake_dark.toml in dark mode and themes/handshake_light.toml in light mode, unless a [theme] selector chooses another file. Those files use the same config tables, so they can also be imported directly. A full palette import applies the same colors in both appearances. Partial imports and local overrides replace only supplied colors; omitted colors retain the corresponding default theme values.

For example, the default dark theme contains:

[terminal.colors]
background = "#262626"
foreground = "#faf1f3"
cursor = "#007aff"
selection = "#3f638b"
black = "#1c1c1c"
red = "#ff8d7a"
green = "#00d9b2"
yellow = "#eba800"
blue = "#5b98e6"
magenta = "#ff82b3"
cyan = "#00cafa"
white = "#faf1f3"
brblack = "#abb3cd"
brred = "#ffaea0"
brgreen = "#00df75"
bryellow = "#ffd166"
brblue = "#82b7ff"
brmagenta = "#d896fe"
brcyan = "#62e3ff"
brwhite = "#ffffff"

Colors must be #RRGGBB strings. Set ANSI colors individually with black, red, green, yellow, blue, magenta, cyan, and white. Bright variants use the br prefix: brblack through brwhite. Legacy ansi arrays remain readable; named colors override their corresponding slots. The same tables and keys work in config.toml and all imported files. Saving settings in Handshake updates shell and agent terminals, Bento panes, saved output, and minimaps.

Omitted settings use defaults. Invalid TOML, invalid values, or file errors (including theme files) use the complete defaults; unknown keys are ignored with a warning. Diagnostics include the file, line, and key (or <document> when a syntax error has no identifiable key). They appear in macOS Console under the com.twineproject.Twine subsystem, without logging config values.

Browser tabs and media previews

Use the globe button beside +, or ⌥⌘T, to open a browser tab. Enter a website address; bare addresses use HTTPS, and localhost and loopback addresses use HTTP. Use Back, Forward, Reload/Stop, and ⌘L for the address field. The Browser menu provides ⌘[, ⌘], and ⌘R. ⌘T still creates a workflow.

Each tab keeps its page and history while you switch tabs or sessions. Website popups open sibling tabs; website dialogs and file uploads use native sheets. Browser tabs share WebKit's normal persistent website data. Browser renaming, reordering, pinning, search, reopening, and restoration are available by default. Restoration loads the saved page address; it does not restore an in-memory form or page history.

Open PDFs, images, and videos from the Files sidebar to preview them in file tabs. PDFs use the native document viewer; images fit the available space; videos have playback and seek controls and pause when hidden. These previews are not subject to the text editor's 2 MiB limit. Playback depends on the system's supported codecs. Text images such as SVG retain their Source editor.

Agent browser control (beta)

Agent browser control lets coding agents use the embedded browser while you watch. It is a beta and is off by default. Turn on Agent browser control in Settings → Experimental, then start a new terminal or agent. Ordinary browser tabs work without it. Turning it off immediately ends every agent's control and keeps the pages open.

Agents that Handshake starts or resumes receive browser instructions automatically. Codex and Claude Code also get a browser tool for the session; their sandbox and permission settings don't change. From any Handshake terminal, use the bundled command-line tool, which lists its commands with "$HANDSHAKE_CLI" browser --help:

"$HANDSHAKE_CLI" browser open http://localhost:4173
"$HANDSHAKE_CLI" browser --tab ID snapshot
"$HANDSHAKE_CLI" browser --tab ID click e7

An agent can operate only the tabs it opens. Commands cover navigation, page snapshots, clicks, typing, hover, dropdowns, key presses, scrolling, screenshots, waits, and console messages. The browser shows which terminal controls it; Stop / Take over cancels pending commands and ends that terminal's control while leaving the page open. Passwords, dialogs, and uploads require you.

Other sandboxed agents may need approval to run the command-line tool outside their sandbox, so it can reach Handshake. Approve that specific command when the agent asks; you don't need to turn off the whole sandbox.

Tab management

Tab management is available in every folder, including custom workflow and browser names, drag reordering, pinned tabs, a searchable open-tab list, completion indicators, and reopening closed tabs. There is no experimental feature to enable. Existing tab_management configuration entries are ignored.

Double-click a workflow or browser tab or choose Rename… from its context menu. Choose Reset Name to return to its automatic name. File tabs keep their filenames; duplicate filenames show enough parent folders to distinguish them. Drag tabs to reorder, or use Move Left/Right in the context menu. Pinned tabs stay at the leading edge. Names, order, pins, open files, browser page addresses, and the selected tab are remembered across relaunch. Top-level tabs show a Done marker after completion; agent status inside multi-agent workflows remains visible.

New Terminal starts a fresh shell; a single-agent workflow also offers an explicit Resume Session… action. Recently closed history keeps up to 20 entries. Saved output remains subject to transcript retention. Reopening a file reloads its saved content; discarded edits are not restored.

Terminal panes#

Use the two buttons at the top right, ⌘D to split right, or ⇧⌘D to split down. Each split starts a shell in the same folder; run any command or coding agent there. Up to four panes share the same Bento styling and draggable dividers as agent workflows. ⌘[ and ⌘] move keyboard focus. Each pane has a close button; ⌘W closes the focused pane, and closing the tab closes its panes. Pane layouts survive reopening. The Traces panel combines all panes in a tab into one set of tracks, and selecting an event focuses its owning pane.

Paste a clipboard screenshot with ⌘V, or drop images and files onto any terminal or agent pane. Clipboard images become private PNG files under the app data directory’s attachments/ folder; Handshake inserts their quoted paths so the shell or harness can read them. File drops use their original paths. How much output remains in live scrollback depends on the harness's terminal display mode.

Terminal transcripts#

Every terminal and agent pane has a compact minimap at its right edge. Hover or focus the 14-point rail to expand it over the output; expansion does not change the terminal's columns. Click or drag the visible-region indicator to scroll. With the rail focused, use the arrow, Page Up/Down, Home, and End keys. Return to live resumes following the latest output. Each Bento pane keeps its own position.

Minimap points use the same step IDs, numbers, role colors, and selection as Traces. Selecting a point opens that step in Traces and scrolls the live terminal to its recorded position. Points are placed by terminal row; the Traces panel spaces steps by start order. Loading Older traces adds those steps to the map when their output is still available. Output without an available anchor remains scrollable without a guessed point. Historical output also has its own minimap.

Handshake saves terminal output under ~/Library/Application Support/Handshake/transcripts/. Terminal IDs remain unique across launches. Closing a terminal preserves output already accepted for recording. Reopening a folder restores recorded output and scrollback. Shells append a fresh prompt. Single agents resume their exact recorded harness session, retaining earlier output. Codex and Claude Code use session IDs; pi and OMP use session files. Kiro conversations started in Handshake restore both their exact session ID and managed profile identity. Antigravity and OpenCode support exact-ID resume but don't expose launch observers, so use Resume Session… to supply the conversation/session ID once. The same action is available for older tabs without a captured session. Handshake never guesses the latest conversation. Cancelled or failed agents remain stopped. Saved output opens earlier invocations, including an idle shell with no trace step. Live views and ANSI replay retain up to 100,000 rows in memory; the raw transcript limits below apply independently. New workflows appear in Traces once their terminals are active.

Saved output is capped at 64 MiB per terminal and 512 MiB across all terminals. Older output expires when storage or metadata limits are reached. Expired output remains unavailable after reopening Handshake.

Click an anchored event in trace details to select its workflow and agent and scroll the mounted terminal to that point. Return to live scrolls back to the latest output. If a point belongs to an earlier invocation or has left scrollback, Handshake opens a read-only snapshot of the saved output instead. A restored workflow's Saved output menu opens earlier invocations. Saved output replays cursor movement and recorded terminal sizes; resizing the window only changes its viewport. It displays text without terminal colors or images. Events without an anchor keep their details without a jump action.

Saved output needs the earlier terminal output and its recorded sizes to display correctly. If either has expired, Handshake shows Output no longer available.
