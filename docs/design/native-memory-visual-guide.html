Where everything lives

Production memories use Twine’s application-support directory. Test and trial data can explicitly override it.

~/Library/Application Support/Twine/memories/
memories/
├── bindings.sqlite                  Local project policy and receiver bindings
└── projects/<project UUID>/
    ├── library.amis.json             Canonical memories + complete history
    ├── bindings/                     Local identity reservations and recovery
    ├── blobs/                        Exact native before/after bytes
    ├── journal/                      Sealed plans + local policy decisions
    ├── receipts/                     Native-byte verification
    └── native/codex/                 This project’s native CODEX_HOME

Claude: ~/.claude/projects/twine-<project UUID>/memory/, with a managed index link and native topic files.

Codex: Twine delivers native inputs under memories/extensions/ad_hoc/notes/. Codex owns its generated MEMORY.md and memory_summary.md. Twine does not replace those generated files.

Credentials and settings are reused; memory files are isolated by project. A standalone CLI session uses its usual profile unless launched through Twine. This is local sharing on one Mac, without a cloud memory service.

How edits, forgetting and feedback are handled
  • Unchanged owned projections are recognized as exports and skipped. Their metadata cannot become a fresh independent source.
  • Editing a uniquely attributable native topic appends a revision to its original identity. Ambiguous or concurrent edits are held and preserved.
  • Codex’s managed native registry is captured as a source snapshot. Its delivered Twine ancestry is recorded, and that registry snapshot is exported to Claude without feeding it back into Codex’s own inputs.
  • Deleting a native source does not silently withdraw history. Explicit withdrawal appends durable withdrawal revisions and native corrections, including owned original source notes.
  • Twine holds a native session lease through child startup and lifetime. The worker waits before changing that harness’s native files; it retries automatically after the session ends.
  • Exact duplicate text can share one consolidated view. Semantically similar or contradictory text stays separate; Twine does not run an LLM to choose which claim is true.

What UX testing caught
  • Fixed: Claude’s directory alias depended on a config-root override that changed authentication/config lookup. Twine now selects the documented native memory directory through invocation-only settings, preserving its observer hooks.
  • Fixed: status polling could overwrite a policy action, and the new panel initially lost the existing 200% zoom bounds.
  • Fixed: an active harness could block delivery and index updates for the other harness. Independent targets now continue and held targets retry.
  • Still visible: Codex’s first native background pass can delay startup availability. This small trial was prepared with one brief native startup turn; its native memory is ready.
  • Still visible: consolidation merges exact text only. A native summary can overlap source memories and appear as another derived view. The two seeded trial facts currently produce three views after Codex’s native summary is captured.

Validation from this implementation

Both directions were exercised with two tiny fictional memories. Native file delivery, native generation and fresh-session recall were checked separately.

  • 23 focused Rust contract, native projection, isolation and recovery checks passed, plus launch-setting and hook-preservation tests.
  • Three real macOS UX tests passed: automatic two-way sharing and relaunch, pause/resume, and 200% zoom. Fresh Codex recalled the Claude-origin account code; fresh Claude recalled the Codex-origin deployment lane with two native reads. Codex weekly usage stayed at 88% in the tiny recall run.
